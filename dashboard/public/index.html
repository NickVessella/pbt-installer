Executive Summary

Plan-Build-Test (PBT) is a structured coding workflow that runs inside AI coding agents. It triages every coding request by complexity, enforces a plan-then-build-then-test discipline, and logs structured metrics after each task. The result is fewer follow-up prompts, fewer missed bugs, and a growing dataset of how your agent actually performs.

How It Works
1
Triage
Every coding request is classified before any tool call into one of four tiers: Trivial, Small Scope, Complex, or Investigative.
2
Plan
Small Scope and above produce a plan before code is written. Plans include goal, files, approach, risks with resolutions, and test strategy.
3
Build
Implementation follows the plan's file list as a checklist. Deviations are noted with a reason.
4
Test
Mandatory build gate, runtime gate, existing tests, new tests for new behavior, linter pass, and visual verification for UI changes.
5
Log
Every task appends a structured JSON entry to ~/.pbt-log.jsonl. The task is not complete until the log is written.
Triage Tiers
Trivial
1–2 files, no design decisions, obvious single implementation. Make the change directly, log, done.
Small Scope
1–3 files, straightforward logic in existing patterns, low risk. Abbreviated plan, then build and test.
Complex
3+ files with logic changes, new modules or architectural patterns, multiple valid approaches. Full plan with risks and test strategy.
Investigative
Root cause unknown, visual/layout bugs where rendering is the unknown, 2+ prior failed attempts. Spike first, then plan-build-test.
Key Mechanisms
Retry Escalation
The log doubles as memory. Before triaging, PBT checks the last 3 log entries for prior attempts. One prior attempt bumps the tier one level. Two or more bumps to Complex (or Investigative for visual tasks).
Speculation Circuit Breaker
If the plan uses hedging language about runtime behavior, planning stops. The agent must ask the user or escalate to Investigative.
Visual Task Detection
Requests involving positioning, alignment, layout, animation, CSS, or visual appearance force visual verification regardless of tier.
Spike Protocol
Investigative tasks run a structured spike: hypothesis → code change → observe → repeat (3 attempts max). All spike changes are reverted before the clean build.
Bugfix Cascade Rule
When the user reports an error, every fix must pass the build gate and runtime gate before reporting back. Two consecutive errors triggers escalation.

Installation & Setup
1. Install the Skill
One line installs PBT as a Cursor skill into ~/.cursor/. Idempotent — safe to re-run.
curl -fsSL https://raw.githubusercontent.com/NickVessella/pbt-installer/main/install.sh | bash
2. Mode Gate (Cursor)
PBT only activates in Agent mode. Plan, Debug, and Ask modes skip the workflow entirely.
.cursor/rules/plan-build-test.mdc
→ gates on Agent mode only
3. Optional: Slack Alerts
Set $PBT_SLACK_WEBHOOK to receive a Slack message after each logged task.
export PBT_SLACK_WEBHOOK=https://hooks.slack.com/...
Design Philosophy
Classify from the request, not the code
Triage happens before any tool call. Reading code to reduce triage uncertainty is explicitly prohibited — a wrong tier is cheap to escalate, but a pre-triage tool call is an unrecoverable violation.
Plans are contracts, not suggestions
The plan's file list is a checklist for the build phase. Deviations are allowed but must be noted. Skipping a planned file requires a written reason.
Done means logged
A task is not complete until the structured log entry is written. No exceptions. This turns every session into a data source for future triage accuracy and workflow optimization.
